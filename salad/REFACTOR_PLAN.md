# Vast を正本にする SaladCloud 構成へのリファクタリング計画

## 目的と確定した方針

- Vast.ai をメイン環境とし、モデルの設定・セットアップ・実行手順はルートの `models/` を正本にする。
- ルートの `vast/` をなくし、現在の `vast/models/` と `vast/tools/` をそれぞれルートの `models/` と `tools/` に移す。移設するファイルの**内容は変更しない**。
- `salad/` は従来の場所に残し、Dockerfile、起動ラッパー、Gateway 認証など SaladCloud 固有の処理をここに集める。
- SaladCloud 用の Dockerfile は一つにする。Vast の PyTorch テンプレートが提供する Python、CUDA、システムツール、パスを再現し、モデルごとの設定は同じ `models/<モデル>/setup.sh` から行う。
- モデルの重みと生成物はイメージに含めない。モデル選択は起動時の明示的な設定とし、未指定・未対応なら起動を失敗させる。

## 目標構成

```text
repository-root/
├─ models/                 # 旧 vast/models。既存ファイルの内容は変更しない
├─ tools/                  # 旧 vast/tools。既存ファイルの内容は変更しない
├─ scripts/                # 既存の共通セットアップ処理
├─ local_tools/            # ローカル PC 用。今回の移設対象外
└─ salad/
   ├─ Dockerfile           # 共通の PyTorch/CUDA/Python 実行環境
   ├─ entrypoint.sh        # モデル選択、起動、終了管理
   ├─ common/              # Gateway 認証など Salad 固有処理
   └─ tests/               # オフライン検証
```

## 実装前に解く互換性の課題

1. **パス**: Vast のスクリプトは `/workspace`、`/venv/main/bin/python` を前提とする。`qwen-image-edit-2511/setup.sh` は自身の位置から `../../..` でリポジトリルートを計算するため、`vast/models` から `models` へ単純移動すると参照先がずれる。ルート `models/` 内の既存ファイルを変更せず、Salad の起動ラッパーと実行時の互換パスで吸収する。Vast 側で直接実行する場合も同じ問題があるため、移設後の呼び出し方法を検証してから旧階層を削除する。
2. **依存環境**: 現在の Salad イメージはモデルごとに依存をビルド時に導入し、2511 は異なる PyTorch/CUDA ベースを使う。一方、Vast のスクリプトは共通の PyTorch テンプレートを前提としている。共通イメージの Python・CUDA・torch の組み合わせを Vast の実際のテンプレートに合わせ、各 `setup.sh` が依存を導入した後に衝突がないかモデルごとに確認する。既存の 2511 専用構成が不要と実証されるまでは稼働中のイメージ参照を切り替えない。
3. **プロセス**: Vast の `setup.sh` は ComfyUI をバックグラウンド起動して終了するものがある。Salad のラッパーは認証付き Gateway を起動し、ComfyUI の生死を監視し、SIGTERM 時に全子プロセスを終了させる。既存の Vast スクリプトの起動・再起動と競合しないようにする。
4. **起動時間と保存**: セットアップと巨大モデルの取得を起動時に行う構成では、再配置後もダウンロードが発生し得る。準備中の readiness は失敗状態と区別し、失敗時に公開ポートを開かない。出力とモデルの永続化は別途設計し、共通イメージ化だけで永続化されるとは扱わない。
5. **対象モデル**: 現在の `salad/models` には Vast 側に同名のセットアップがない BFS などがある。Vast の `models/` を正本として直接呼べるモデルと、Salad 固有の処理が必要なモデルを一覧化する。後者は `salad/` 内にアダプターを置き、既存 `models/` の内容を変更しない。

## 実装順序

1. 移設前の追跡ファイル一覧、内容ハッシュ、参照箇所、ユーザー変更・未追跡ファイルを記録する。既存のユーザー変更は巻き込まない。画像ファイルには触れないというリポジトリ規則を守り、移設対象に画像がある場合はその扱いを先に確定する。
2. `vast/models` と `vast/tools` をルートへ移設する。移設元のファイル内容を変えず、`vast/` を残す参照をコード、テスト、CI、ドキュメント、運用コマンドから更新する。旧 `vast/` は参照がなくなってから削除する。
3. `salad/Dockerfile` で Vast テンプレート相当の土台を一度だけビルドする。リポジトリのスクリプトは実行時に利用可能にし、モデルごとの依存・重みをイメージビルドに組み込まない。
4. `salad/entrypoint.sh` にモデル選択、既存 Vast セットアップの呼び出し、認証付き Gateway、ヘルスチェック、シグナル処理を実装する。モデル固有の差分は必要なものだけ `salad/` に置く。
5. CI を単一イメージのビルドへ変更し、モデル別 Dockerfile と重複した Salad セットアップを、互換性の検証後に削除する。Container Group のイメージ参照を一斉に変更せず、モデルごとに切り替え可能にする。
6. README とリモート環境の実行コマンドを新しい `models/`・`tools/` 配置へ更新する。既存の「SaladCloud対応およびVast階層移動 実装手順書.md」は旧方針の資料として扱い、現行手順への誘導を明記する。

## 検証と切り替え条件

- `models/` と `tools/` に移した各ファイルの内容ハッシュが移設前と一致し、意図した移動以外の差分がないこと。
- すべての変更したシェルスクリプトを WSL で構文検査する。Python、JSON、Actions YAML、Dockerfile の静的検査と、計算・分岐・状態遷移に対応する外部接続なしのテストを実施する。
- モデルごとに、共通イメージ上で Vast の `setup.sh` が参照するパス・コマンド・Python 環境を確認する。可能な範囲でネットワークと GPU を使わない起動経路テストを行う。
- 有料の SaladCloud コンテナ、GPU、実画像生成は検証に使わない。実環境で未確認の項目は明記し、ローカル成功を実環境成功と扱わない。
- `git diff --check`、差分全体、秘密情報・生成物・一時ファイルの混入を確認した後、今回の変更だけを現在の `main` にコミット・プッシュする。未追跡ファイルは含めず、プッシュ前に報告する。

この計画は実装方針であり、この文書の作成時点でディレクトリの移動やイメージの切り替えは行っていない。

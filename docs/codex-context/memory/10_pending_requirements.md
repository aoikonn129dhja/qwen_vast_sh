# Pending requirements

These are the most recent requirements and are **not implemented** in `snapshot/run_batch.sh`.

## A. 5-second browser completion alert

Constraints:
- implement using the existing preview page generated by `run_batch.sh`;
- no new external service;
- no additional normal-operation step;
- no separate audio asset required if Web Audio API is sufficient;
- PC/browser remains open, but preview may be a background tab or minimized;
- alert should last roughly 5 seconds, not a single short beep;
- trigger once when the active batch transitions to complete (`completed_jobs == total_jobs`), not on every poll after completion;
- avoid replaying continuously on page refresh unless the implementation deliberately tracks/guards the completion transition;
- preserve current Basic Auth and preview navigation.

Practical implementation direction:
- create an `AudioContext` lazily/once;
- synthesize a repeated alarm pattern for ~5 seconds;
- track previous completion state and current `run_id` in JS;
- best-effort resume/unlock audio after ordinary page interaction, without adding a mandatory setup step;
- background/minimized behavior must be treated as browser-policy-dependent.

## B. Per-output timing and running average
After each generated image/output finishes, print timing information to the shell.

Required information after every completed output:
- elapsed seconds for that output;
- running average seconds per image so far.

Because the user's parenthetical used `枚/s`, include throughput too if concise:
- `avg_s_per_image`
- `images_per_second = completed / cumulative_seconds`

Suggested human-readable shape (exact wording can vary):

```text
[12/100] done  |  this: 7.42 s  |  avg: 7.18 s/image  |  0.139 image/s
```

Timing boundary should represent one complete job as experienced by the batch runner, preferably from immediately before workflow submission/execution to after the output flush/move for that job. Be explicit in code comments if a different boundary is chosen.
